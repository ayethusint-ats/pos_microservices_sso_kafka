# Phase 2 — User Service and Account Service

## 1. Concept: a service is a small, layered, self-contained app

Each microservice is a complete Spring Boot application with its own port, its own database, and its own build. Inside, we use a classic **layered architecture**:

```
HTTP request
   │
   ▼
Controller    @RestController       URL → method, @Valid, status codes. No business logic.
   │  DTO (record)
   ▼
Service       @Service              Business rules, @Transactional boundary, orchestration.
   │  Entity
   ▼
Repository    JpaRepository         Data access, generated by Spring Data.
   │
   ▼
Database      H2 now → PostgreSQL in Phase 3
```

Two cross-cutting pieces:
- **Mapper:** converts entities to and from DTOs. The API contract never exposes JPA entities.
- **GlobalExceptionHandler** (`@RestControllerAdvice`): turns exceptions into RFC 9457 `application/problem+json`.

## 2. Why these two services first

They are the core data owners. Every later feature (payments, history, authorization) depends on knowing *who* the customer is and *which* accounts they own.

| | user-service (8081) | account-service (8082) |
|---|---|---|
| Owns | Customer profile | Accounts and balances |
| Identity link | `keycloakUserId` = JWT `sub` | `ownerId` = JWT `sub` |
| Key rule | One profile per identity, unique email | Balance never negative, amounts > 0 with max 2 decimals, only ACTIVE accounts move money |

**Design decision: `ownerId` is the Keycloak `sub`, not the user-service customer id.** In Phase 8, account-service can check "is this your account?" with `account.ownerId == jwt.sub`, without calling user-service. That keeps services decoupled and avoids a network hop on every request.

## 4. Request flow: `POST /api/accounts/{id}/withdraw {"amount": 100.00}`

1. **DispatcherServlet** matches `AccountController.withdraw`.
2. **Jackson** turns the JSON into a `MoneyRequest`. `@Valid` runs Bean Validation (`@Positive`, `@Digits`). On failure → `MethodArgumentNotValidException` → **400** with `errors`.
3. `AccountService.withdraw` runs inside **one DB transaction** (`@Transactional`).
4. `findById` loads the account → **404** if missing.
5. `account.withdraw(amount)` applies the domain rules → **422** `INSUFFICIENT_FUNDS` / `ACCOUNT_NOT_ACTIVE`.
6. `flush()` sends `UPDATE accounts SET balance=?, version=version+1 ... WHERE id=? AND version=?`. If another request changed the row first → **409**.
7. Commit. The mapper builds an `AccountResponse` → **200**.

## 5. Important annotations and configuration

| Item | Why |
|---|---|
| `@Transactional(readOnly = true)` on the class, `@Transactional` on writes | Read-only is the safe default and lets Hibernate skip dirty checking. Writes opt in explicitly. |
| `@Version` | Optimistic locking against lost updates. See `OptimisticLockingTest`. |
| `@Enumerated(EnumType.STRING)` | Stores `"SAVINGS"`, so reordering the enum can't corrupt data (ORDINAL would). |
| `BigDecimal` + `precision=19, scale=2` | Exact decimal math. `0.1 + 0.2 != 0.3` with `double`. |
| `@GeneratedValue(strategy = UUID)` | IDs can't be guessed or enumerated (unlike 1, 2, 3…), and can be generated without the DB. |
| `@Embeddable Address` | A value object stored as columns in `customers`, with no extra table or join. |
| `saveAndFlush()` / `flush()` | Forces the SQL now, so constraint and lock errors surface inside the service and generated timestamps are filled before mapping. |
| `spring.jpa.open-in-view: false` | Stops lazy-loading SQL from running while JSON is rendered (a hidden N+1 source). Boot warns if you leave it on. |
| `ddl-auto: create-drop` | **Dev only.** Phase 3 switches to Flyway migrations + `validate`. |
| `max-page-size: 100` | A client can't request `?size=1000000`. |
| `PageResponse` record | A stable JSON contract instead of serializing Spring's `PageImpl`. |
| Constructor injection | Final fields, explicit dependencies, and the class can be built with `new` in unit tests. |

### Status code policy

| Situation | Status |
|---|---|
| Created | 201 + `Location` |
| Deleted | 204 |
| Malformed JSON, invalid field, bad UUID, unknown enum | 400 |
| Not found | 404 |
| Duplicate email/identity, concurrent update | 409 |
| Valid request that breaks a business rule | 422 with `code` |
| Unexpected | 500, generic message (details only in logs) |

## 6. How the services communicate

They don't yet, and that's intentional. Phase 9 adds payment-service → account-service over REST. For now the only link is the shared identity value.

## 7. Running

```bash
cd banking-platform
mvn verify                                  # builds both, runs 27 tests

# Terminal 1
mvn -pl user-service spring-boot:run
# Terminal 2
mvn -pl account-service spring-boot:run
```

`mvn -pl <module>` builds and runs only that module. Health checks: `curl localhost:8081/actuator/health`, `curl localhost:8082/actuator/health`.

## 9. Common errors and troubleshooting

| Symptom | Cause / fix |
|---|---|
| `Port 8081 was already in use` | Another instance is still running: `lsof -i :8081`, then kill it. |
| `415 Unsupported Media Type` | Missing `-H 'Content-Type: application/json'`. |
| `400` with no `errors` field | The JSON itself is malformed or an enum value is unknown (e.g. `"type":"GOLD"`). Check quotes and commas. |
| `LazyInitializationException` | You touched a lazy relation outside a transaction. Map to DTOs **inside** the service. |
| Data disappears on restart | Expected: H2 in-memory with `create-drop`. Fixed in Phase 3. |
| `Mockito is currently self-attaching…` | Handled in the root POM by loading Mockito as a `-javaagent`. |
| Entity changes not saved | Your method isn't `@Transactional`, or it's called from inside the same class (self-invocation skips the Spring proxy). |

## 10. Known gaps (closed in later phases)

- **No security.** Anyone can read any customer or move money. → Phases 5 and 8.
- **Client supplies `ownerId` / `keycloakUserId`.** → Phase 8 takes them from the JWT.
- **account-service doesn't check that the owner exists.** → A design choice: Keycloak is the source of identity, so no sync call is needed.
- **Retrying a deposit deposits twice.** → Idempotency keys, Phase 13.
- **Deposits and withdrawals aren't recorded in history.** → Events to Kafka, Phase 11.
- **Customer DELETE is a hard delete.** Real banks keep records for years for regulatory reasons, so production would soft-delete or deactivate.

## 11. Interview questions

1. Why use DTOs instead of returning JPA entities from controllers? (Hint: API stability, over-exposure, lazy loading, mass assignment.)
2. What is the difference between `@Transactional(readOnly = true)` and no transaction?
3. Explain optimistic vs pessimistic locking. When would you choose `SELECT … FOR UPDATE`?
4. What is a "lost update", and how does `@Version` prevent it?
5. Why is `BigDecimal` used for money? What does `compareTo` vs `equals` do with `1.0` and `1.00`?
6. 400 vs 409 vs 422: when do you use each?
7. Why does `@Transactional` not work when a method calls another method in the same class?
8. What does `open-in-view` do, and why disable it?
9. Why validate in both the DTO (`@Positive`) and the entity (`requireValidAmount`)?
10. Rich vs anemic domain model: which did we use for `Account`, and why?
11. Why use the Keycloak `sub` as `ownerId` instead of the user-service customer id?
